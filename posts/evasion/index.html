Mythic C2 : Evading Advanced Detection Systems (Part 1)

This is the continuation of this article

Advanced Detection Systems are a real headache for red teamers (as they should be). Modern environments aren’t just relying on static AV anymore, you’re dealing with layered detection: AV, EDR, SIEM correlation, sometimes even behavioral ML on top.

So instead of trying to “bypass everything” (which is unrealistic), the idea here is to reduce your footprint at each layer.

In this part, I focused on a few steps that already make a big difference in a real-world engagement. But before going into infra and traffic shaping, the first obvious checkpoint is: does the payload even survive basic AV?

Now that I made my own agent for Mythic, the goal is to make it less obvious to monitoring solutions, both at rest and in transit.

Bypassing AVs

Before doing anything fancy, I checked my payload against VirusTotal. No surprises here; it got picked up by a couple of engines:

At this stage, this is mostly signature + heuristic detection. Even a custom agent can still trigger flags depending on how it’s packaged.

I tried a couple of approaches, starting with PyInstaller, but I found that Nuitka gave noticeably better results:

The reasoning here is pretty straightforward:

  • PyInstaller bundles Python bytecode -> easier to fingerprint
  • Nuitka compiles to C -> then to machine code -> significantly less “Python-looking” artifacts

That alone reduces the number of trivial detections.

Here’s the command I used to generate a Windows executable:

python -m nuitka \
  --standalone \
  --onefile \
  --windows-console-mode=disable \
  --python-flag=no_site \
  --python-flag=no_warnings \
  --python-flag=isolated \
  --nofollow-import-to=tkinter \
  --nofollow-import-to=unittest \
  --enable-plugin=anti-bloat \
  --windows-company-name="Microsoft Corporation" \
  --windows-product-name="Windows Host Process" \
  --windows-file-version=10.0.19041.1 \
  --windows-product-version=10.0.19041.1 \
  --windows-file-description="Windows Host Process (Rundll32)" \
  --output-filename=RuntimeBroker.exe \
  agent.py

A couple of important details here:

  • Metadata spoofing (company name, product name, etc.) helps blend into legitimate binaries
  • Anti-bloat plugin reduces unnecessary imports -> smaller surface for static analysis
  • Isolated Python flags remove environmental dependencies that can leak indicators

Writing your own agent already helps with AV evasion since there are no public signatures tied to it. That said, Mythic’s base implementations are still relatively well-known, so don’t assume you’re safe just because it’s “custom”.

Azure Setup

I won’t go too deep into Azure provisioning. This isn’t a cloud tutorial, just enough to get a realistic infra in place.

We need a VM to host the C2 server. Minimum specs:

  • 2 CPUs
  • 4 GB RAM

I went with Ubuntu, 2 CPUs and 8 GB RAM just to keep things smooth during deployment and testing:

No need for extra disk space, default boot disk is enough.

For networking, open:

  • SSH (management)
  • HTTP / HTTPS (C2 traffic)
  • Mythic UI (optional)

I restricted the Mythic UI to my own IP. This reduces exposure significantly, but only makes sense if your IP is relatively stable, otherwise it becomes annoying quickly.

Then you can just follow the install steps from this article.

CDN Setup

This is where things start getting interesting from an evasion standpoint.

The goal here is simple: don’t expose your origin server directly.

Before using a CDN, a simple DNS lookup returns your actual Azure IP:

That’s bad, defenders can:

  • pivot directly to your infra
  • scan your server
  • correlate infrastructure across engagements

So we put a CDN in front.

First, you’ll need a domain. I just bought a cheap one (~$1). Free subdomains can work, but I ran into issues integrating them cleanly with Cloudflare.

After onboarding your domain in Cloudflare:

  • Enable automatic DNS import
  • Replace your registrar’s nameservers with Cloudflare’s

Then… wait. DNS propagation can take awhile.

Once everything is set, querying your domain now returns Cloudflare IPs instead of your VM:

This gives you:

  • Origin IP masking
  • Basic traffic normalization
  • A layer between you and direct attribution

Not bulletproof, but way better than exposing your VM raw.

HTTP Profile Setup

Now we move to traffic legitimacy.

Using plain HTTP in 2026 is basically asking to get flagged. So we switch to HTTPS with valid certificates.

First, generate certs using certbot:

sudo apt-get install -y certbot
sudo certbot certonly --register-unsafely-without-email \
  -d your.domain

Then copy them into the Mythic HTTP profile:

sudo cp /etc/letsencrypt/live/YOURDOMAIN/fullchain.pem .
sudo cp /etc/letsencrypt/live/YOURDOMAIN/privkey.pem .

# Copy certs into HTTP C2 container
sudo docker ps | grep http
sudo docker cp fullchain.pem CONTAINER_ID:/Mythic/http/c2_code/fullchain.pem
sudo docker cp privkey.pem CONTAINER_ID:/Mythic/http/c2_code/privkey.pem

Update the HTTP profile config:

{
    "instances": [
        {
            "port": 443,
            "key_path": "privkey.pem",
            "cert_path": "fullchain.pem",
            "debug": true,
            "use_ssl": true,
            "ServerHeaders": {
                "Cache-Control": "max-age=0, no-cache",
                "Connection": "keep-alive",
                "Content-Type": "application/javascript; charset=utf-8",
                "Pragma": "no-cache",
                "Server": "NetDNA-cache/2.2"
            },
            "error_file_path": "",
            "error_status_code": 404,
            "payloads": {}
        }
    ]
}

Important points:

  • Port 443 -> blends with normal HTTPS traffic
  • Valid TLS cert -> avoids TLS inspection flags
  • Custom headers -> helps mimic legitimate CDN/web traffic

When generating payloads:

  • Use your domain, not the IP
  • Use https://, not http://

Otherwise, the CDN + TLS setup becomes useless.

Closing Thoughts

This part is mostly about infrastructure-level evasion:

  • Reducing AV detections (payload side)
  • Hiding origin infrastructure (CDN)
  • Making traffic look legitimate (HTTPS + headers)

It’s far from enough on its own.

Detection today is heavily behavioral, so even with clean infra, bad tradecraft will still get you caught.

Next parts will go deeper into:

  • traffic shaping
  • beacon design
  • and ways to reduce behavioral indicators
